# Домашнее задание к занятию «Введение в микросервисы»

## Задача

Руководство крупного интернет-магазина, у которого постоянно растёт пользовательская база и количество заказов, рассматривает возможность переделки своей внутренней   ИТ-системы на основе микросервисов. 

Вас пригласили в качестве консультанта для оценки целесообразности перехода на микросервисную архитектуру. 

Опишите, какие выгоды может получить компания от перехода на микросервисную архитектуру и какие проблемы нужно решить в первую очередь.

# Выполнение

Переход даст выгоды, но в первую очередь нужно решить проблемы, которые могут сделать проект провальным.

1. Выгоды для бизнеса:
   - Масштабируемость по требованию: Можно масштабировать только сервис "Корзина" в час пик, не увеличивая ресурсы для сервиса "Доставка" или "Каталог". Это экономия на инфраструктуре.

   - Скорость вывода фич: Разные команды могут разрабатывать, деплоить и обновлять свои сервисы независимо (например, команда оплаты не ждет команду логистики).

   - Устойчивость к сбоям (Fault Tolerance): Если упадет сервис "Рекомендации", магазин продолжит принимать заказы. В монолите падение одной функции часто роняет весь сайт.

   - Технологическая гибкость: Можно писать сервис обработки платежей на Go (для производительности), а сервис отчетности на Python (для аналитики), не привязываясь к одному стеку.

2. Выгоды (долгосрочные):
   - Возможность легкого аутсорсинга (можно отдать разработку сервиса "Чат поддержки" сторонней фирме, не давая им доступ к коду всей системы).

   - Оптимизация затрат на облако (автоскейлинг по метрикам CPU/RPS).

3. Критические проблемы:

   - Распределенные данные: У сервиса "Заказы" и "Склад" не может быть одной общей базы данных (это антипаттерн). Нужно решить, кто владеет данными о товаре. Требуется наладить взаимодействие и синхронизацию через события (Event Sourcing).

   - Версионирование API: Пока обновляется сервис "Каталог" для нового мобильного приложения, старый сервис "Поиск" может сломаться. Нужно внедрять управление версиями (v1/v2) и обратную совместимость.

   - Команды должны стать кросс-функциональными (включать разработчиков, тестировщиков и DevOps). Если оставить централизованный отдел тестирования, который тестирует всё вместе, то потеряется скорость, ради которой затевался переход.

4. Задачи:
   - 0: Необходимо инвестировать в CI/CD и систему мониторинга (Observability), иначе микросервисы превратятся в "кошмар распределенных отладок", который убьет бизнес быстрее, чем текущий монолит.
   - А: Доменнная модель (DDD). Нельзя просто "нарезать" монолит по контроллерам. Нужно четко определить границы контекстов (Заказы, Клиенты, Склад, Платежи и т.п.). Если границы выбраны неверно - микросервисы будут слишком "связанными" и превратятся в "распределенный монолит".
   - Б: API Gateway. Нужно внедрить точку входа (например, Kong или Spring Cloud Gateway), чтобы клиенты (фронтенд, мобильное приложение) не знали, где находится каждый из 20 сервисов, и чтобы централизовать аутентификацию.
   - В: Переход на асинхронность. Для интернет-магазина критично использовать очереди (Kafka/RabbitMQ) для операций, не требующих мгновенного ответа (отправка писем, генерация чеков, обновление статистики), чтобы не держать пользователя в ожидании.
