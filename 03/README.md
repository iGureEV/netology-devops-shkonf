# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

# Выполнение ДЗ №3

## Задача 1. Обеспечение разработки (CI/CD)

Выбранное решение: GitLab (Self‑hosted или SaaS) + GitLab CI/CD + GitLab Container Registry (опционально Harbor).  

Обоснование выбора:
- Единая платформа - закрывает все потребности: хранение Git-репозиториев, CI/CD, реестр образов, управление секретами.
- Гибкость - поддерживает все перечисленные требования:
  - отдельный репозиторий на сервис;
  - автоматический запуск по push, merge request, тегам;
  - ручной запуск с параметрами (переменные);
  - шаблоны (include, extends) для переиспользования;
  - безопасное хранение секретов (защищённые переменные, интеграция с Vault);
  - несколько конфигураций из одного репозитория (разные rules, only/except);
  - кастомные шаги (любые скрипты);
  - использование собственных Docker-образов в качестве среды выполнения;
  - развёртывание раннеров на своих серверах (поддерживаются Docker, Kubernetes, Shell);
  - параллельные джобы и тесты.
- Интеграция с Kubernetes - позволяет разворачивать сервисы прямо из пайплайна (через Helm или kubectl).
- Container Registry - встроенный реестр для хранения Docker-образов. При необходимости можно дополнить Harbor для расширенного сканирования уязвимостей и строгой политики безопасности.

Альтернативы (отклонены):
- Jenkins - требует больше ручной настройки, слабее в управлении репозиториями, нет встроенного реестра.
- GitHub Actions - удобен, но при self‑hosted теряет часть облачных преимуществ, а GitLab даёт более полный контроль в корпоративной среде.

## Задача 2. Логи

Выбранное решение: Loki + Promtail + Grafana (вместо классического ELK).  

Обоснование выбора:
- Лёгкость и простота - Loki не индексирует содержимое логов, а только метки, что значительно снижает затраты на хранение и ускоряет запись.
- Единый интерфейс - Grafana уже используется для мониторинга (Задача 3), что даёт единую точку входа для разработчиков и администраторов.
- Сбор из stdout - Promtail читает логи контейнеров (Docker, Kubernetes) и файлы, минимальные требования к приложениям.
- Гарантированная доставка - Promtail поддерживает буферизацию и повторные попытки при сбоях; Loki обеспечивает репликацию и устойчивость.
- Поиск и фильтрация - язык запросов LogQL (аналог PromQL) позволяет эффективно искать и фильтровать логи по меткам и содержимому.
- Сохранение поисков и ссылки - в Grafana можно сохранять запросы, создавать дашборды с логами и делиться ссылками на них.
- Ролевая модель - Grafana позволяет разграничивать доступ разработчиков к конкретным источникам данных.

Почему не Kibana / ELK?
- Elasticsearch + Kibana требуют больше ресурсов, сложнее в обслуживании, а с введением SSPL‑лицензии возникают юридические ограничения.
- Использование Grafana как единого фронтенда для логов и метрик упрощает работу команды и снижает число инструментов.

Альтернативы (отклонены):
- ELK (Elasticsearch, Logstash, Kibana) - мощное решение, но избыточно для большинства задач и тяжеловесно.
- OpenSearch - форк Elasticsearch, но всё ещё требует отдельной визуализации (OpenSearch Dashboards).

## Задача 3. Мониторинг

Выбранное решение: Prometheus + Grafana + Node Exporter + экспортёры сервисов.  

Обоснование выбора:
- Сбор метрик - Prometheus собирает данные со всех хостов и сервисов по протоколу HTTP (pull-модель).
- Метрики хостов - Node Exporter предоставляет CPU, RAM, HDD, Network.
- Метрики контейнеров / сервисов - cAdvisor или kube-state-metrics (если Kubernetes) собирают потребление ресурсов каждым сервисом. Для прикладных метрик разработчики реализуют эндпоинт /metrics (библиотеки для всех популярных языков).
- Специфичные метрики - легко добавляются через кастомные экспортёры или прямо в коде сервиса (например, число запросов, длительность, ошибки).
- Хранение и запросы - Prometheus хранит временные ряды, язык PromQL позволяет агрегировать, фильтровать и строить сложные запросы.
- Визуализация - Grafana подключается к Prometheus, предоставляет интерактивные дашборды, настраиваемые панели, алерты.
- Масштабируемость - Prometheus легко кластеризуется через федерацию или Thanos; Grafana поддерживает высокую доступность.

Предпосылки из личного опыта:
- Используется в подавляющем большинстве современных микросервисных проектов, имеет огромное сообщество и готовые интеграции.
- Минимальные требования к приложениям - достаточно выставлять метрики на стандартном порту.

Альтернативы (отклонены):
- Zabbix / Nagios - больше подходят для мониторинга инфраструктуры, но не дают гибкости для прикладных метрик и динамических сред.
- Datadog / New Relic - мощные платные SaaS-решения, но не всегда допустимы по бюджету и политике безопасности в крупной компании.
