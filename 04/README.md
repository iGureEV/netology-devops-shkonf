# Выполнение ДЗ №4

## Задача 1: Кластеризация

Сравнение решений в разрезе требований бизнеса:  

1. Поддержка контейнеров
   - Kubernetes - наиболее гибок, поддерживает любой рантайм, соответствующий CRI (Docker, Container Runtime Interface).
   - Docker Swarm - привязан к Docker, что упрощает развёртывание, но ограничивает выбор.
   - Nomad - может запускать не только контейнеры, но и обычные процессы (Java JAR, бинарники), что полезно для гибридных сред.

2. Обнаружении сервисов и маршрутизация
   - Kubernetes - полный набор: DNS для внутреннего разрешения имён, Service для балансировки, Ingress для внешнего доступа с TLS-терминацией.
   - Swarm - встроенный DNS и Routing Mesh работают только на уровне L4 (TCP/UDP), для L7 требуется внешний прокси (Traefik, NGINX).
   - Nomad - использует Consul как внешний компонент, что даёт более мощные возможности (mTLS, Intentions), но требует отдельного развёртывания Consul.

3. Горизонтальное масштабировани
   - Все три решения поддерживают ручное изменение числа реплик как через CLI, так и через декларативные файлы. Отличий в базовой функциональности практически нет.

4. Автоматическое масштабирование
   - Kubernetes - единственное решение со встроенным HPA, работающим на основе метрик. Дополнительно есть KEDA для событийных сценариев и Cluster Autoscaler для управления нодами.
   - Swarm - не имеет встроенного автскалера, но его можно добавить, написав скрипт, который мониторит метрики и вызывает Docker API для изменения числа реплик. 
   - Nomad - предоставляет отдельный компонент Nomad Autoscaler, который нужно устанавливать и настраивать отдельно.

5. Разделение внешних и внутренних ресурсов
   - Kubernetes - даёт максимальную гибкость: ClusterIP для внутренних сервисов, NodePort/LoadBalancer/Ingress для внешних, а NetworkPolicy позволяет детально управлять доступом на сетевом уровне.
   - Swarm - разделение достигается за счёт внутренних overlay-сетей и публикации портов только для нужных сервисов. Нет встроенных политик безопасности (например, запретить доступ из одного сервиса к другому).
   - Nomad - с Consul Connect можно определить, какие сервисы видны друг другу, и использовать Intentions для разрешения/запрета трафика на уровне L7.

6. Переменные среды и конфигурация  
  Все три поддерживают передачу переменных окружения.
   - Kubernetes - использует ConfigMap для несекретных данных.
   - Swarm - использует environment и confogs.
   - Nomad - в дополнение к env использует Nomad Variables (ключ-значение) для общих конфигураций.

7. Безопасное хранение секретов
   - Kubernetes - базовые Secrets хранятся в etcd (можно зашифровать), но без автоматической ротации. Рекомендуется Vault.
   - Swarm - Docker Secrets обеспечивают хорошую защиту (шифрование, монтирование в tmpfs), но ротация возможна только через создание новых секретов и передеплой сервиса.
   - Nomad - имеет самую тесную интеграцию с Vault, позволяя получать динамические секреты и обновлять их без перезапуска приложений.

Kubernetes - самый сбалансированный выбор закрывающий все требования "из коробка" без необходимости установки дополнительных компонентов (за исключением Vault для усиленной безопасности секретов).  
Docker Swarm подходит для небольших проектов и команд, где важна простота, но он проигрывает в гибкости (особенно в автоматическом масштабировании и сетевых политиках).  
HashiCorp Nomad - отличный выбор для гетерогенных сред (контейнеры + VM) и для тех, кто уже использует Consul и Vault, но требует отдельной настройки автскалера.  

Таким образов, с учётом потребностей и перспектив роста, Kubernetes является лучшим выбором.


## Задача 2: Распредельный кеш

#### Обснование выбора Redis Cluster

- Sentinel - не обеспечивает автоматическое шардирование, все данные хранятся на одном мастер-узле, что ограничивает масштабирование по объёму.
- Codis - требует дополнительного прокси-слоя и Zookeeper, усложняет архитектуру.
- Redis Cluster - нативное решение, встроенное в сам Redis, не требует внешних компонентов, полностью соответствует требованиям по отказоустойчивости и горизонтальному масштабированию.

#### Архитектура

Для распределённого кеша сессий предлагаю классический Redis Cluster с 3 шардами и 3 репликами на шарду, но с размещением на трёх физических хостах (или VM) по следующей схеме, обеспечивающей максимальную отказоустойчивость.

Распределение узлов по хостам
| Хост  | Узлы |
|-------|-------------|
| Host A  | мастер Shard 1 |
|         | реплика Shard 2 |
|         | реплика Shard 3 |
| Host B | мастер Shard 2 |
|        | реплика Shard 1 |
|        | реплика Shard 3 |
| Host C | мастер Shard 3 |
|        | реплика Shard 1 |
|        | реплика Shard 2 |

Каждая шарда владеет примерно третью хэш-слотов (всего 16384).
- Изоляция мастеров - каждый мастер находится на отдельном физическом хосте, что предотвращает одновременную потерю всех мастеров при отказе одного хоста.
- Распределение реплик - реплики шарды размещены на двух других хостах, поэтому при падении одного хоста у каждой шарды остаётся минимум одна работающая реплика.
- Баланс нагрузки - каждый хост несёт нагрузку как мастер для своей шарды, так и реплики для чужих, что равномерно распределяет сетевой трафик и дисковые операции.

#### Механизм восстановления

Redis Cluster использует Gossip-протокол и внутренний алгоритм выборов. При недоступности мастера (timeout) его реплики инициируют голосование, и одна из них становится новым мастером. Весь процесс занимает несколько секунд, что приемемо для кеша сессий (приложения должны быть готовы к кратковременной задержке).

#### Дополнительные меры

- Persistent Volumes - для каждого экземпляра выделяется отдельный том (например, на сетевом хранилище или локальном SSD), чтобы данные не терялись при перезапуске контейнера.
- Политика вытеснения - устанавливаем maxmemory-policy allkeys-lru, чтобы при заполнении памяти удалялись наименее используемые ключи, а не блокировалась запись.
- Мониторинг - разворачиваем Redis Exporter для Prometheus на каждом хосте, чтобы отслеживать: наличие мастеров, синхронизацию реплик, количество ошибок, использование памяти.

#### План разёртывания 

1) На каждом хосте запускаются 3 экземпляра Redis с уникальными портами и конфигурацией cluster-enabled yes.
2) После запуска всех 9 экземпляров выполняется команда создания кластера:
    ```bash
    redis-cli --cluster create \
    HostA:7000 HostB:7000 HostC:7000 \
    HostA:7001 HostB:7001 HostC:7001 \
    HostA:7002 HostB:7002 HostC:7002 \
    --cluster-replicas 2
    ```
3) Проверка: `redis-cli --cluster check HostA:7000`.
